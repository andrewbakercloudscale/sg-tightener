Security Group Console

Every account in the database

The database is the source of truth for security groups: every group and rule, as wanted and as AWS last held it. Changes are change requests: one person proposes, a different person approves, then they are applied. Changes made in AWS outside the tool are found by Refresh from AWS. An account in surveillance mode is only reported on: what to change, and change requests, but nothing is applied. In enforce mode approved changes can be applied, once a permission check (DryRun, nothing changes) shows this identity can make them.

Signs in through your organisation's AWS access portal (IAM Identity Center), the same as aws sso login. You approve it on AWS's own page; the sign-in stays on this computer. Nothing is changed in AWS: the console reads until two people approve a change in an account switched to enforce mode.

Scheduled flow-log reads

While the console runs it reads every chosen account's new flow logs by itself at these times (your computer's clock), so Rejected traffic and the other tabs are up to date when you look. Each read is priced first: within the limit it starts without asking; over it, it waits on this page for you to confirm, as a read you start does. It only reads hours not already read, back as far as Fill back. With read once when it is back ticked, a time missed while the Mac slept (lid closed) or you were signed out of AWS is read once as soon as it is awake and signed in, unless the next scheduled time is under 2 hours away. Unticked, a missed time is only caught up within 6 hours. Signing in to AWS stays your job: the SSO session usually lasts 8 to 12 hours.

How rules are narrowed

Rules per security group: AWS's limit on inbound rules in one group (60 unless your quota was raised). Rules not being narrowed keep their places; the rest is shared between the rules being narrowed so the group as a whole lets in the fewest addresses nobody was seen using. A group that cannot fit is merged down as tightly as the room allows.

Room for unseen addresses: each source seen grows into the widest aligned block (never past its private range, never past the rule it replaces) in which at most this share of addresses was never seen. More room keeps working when a host is replaced at a new address in the same subnet; less lets in fewer strangers. Public addresses always stay single addresses.

Use every free rule for precision: ignores the room above and spends every rule the group has free on letting in fewer never-seen addresses (the fewest possible for that many rules). Tightest, but a new host at a new address will be refused until it is let in again (it shows on Rejected traffic with Fix…).

Outbound rules per port: how many destinations blocks an outbound suggestion may use for each port.

The same settings and maths as sg_tightener.py plan. Saving rebuilds the plan shown; nothing changes in AWS until a change is proposed, approved and applied.

How changes are applied

The order Apply uses when it replaces rules, preselected on Remediate (it can still be changed there for one apply). Add first, then swap adds the new rules while there is room and then removes one old rule per new one, the one with fewest flow-log hits first. Bridge adds a temporary rule spanning old and new sources, swaps underneath it, then removes it. Remove first removes every old rule and then adds: a short gap.

Performance

Reports (Risk overview, Rejected traffic, the address book) are worked out per account in background processes, each holding one account's flow logs (often 1 to 3 GB). More workers finish sooner and use more memory; too many push the Mac into swap and slow everything. Automatic uses at most a quarter of the cores and one worker per 6 GB of memory, at low priority, one report at a time.

Approvals and running

On: a different person must approve each change request before it can be applied. Off suits one person running the console on their own laptop.

Database

Everything (groups, rules, the audit trail, flow logs read, reports) is kept in PostgreSQL. By default a local database in Docker on this Mac. To share one with your team, point every console at the same server: paste its connection string, Test it, then Test and save. It is written to the file shown (readable only by you) and used from the next start. If the environment variable is set, it wins over the file.

Database and computer, now

Database: its size on disk, the rows and storage of each table (rows are PostgreSQL's live count, so close but not exact), connections in use against the most allowed, and the cache hit rate (the share of reads answered from memory: above 99% is healthy; lower means it reads the disk often). Database container: CPU, memory, disk and network of the local PostgreSQL in Docker (shown only when it runs on this Mac); disk and network are totals since it started. Console: this console's own memory and CPU, and the computer's load (processes waiting for a core, averaged over 1, 5 and 15 minutes: under the number of cores is fine). The figures refresh every 15 seconds while this tab is open; Refresh reads them now.

Change requests

Outbound rules that leave the account

Every outbound security group rule, on a group some interface uses, that reaches outside its own account, riskiest first: internet, then SaaS and partners, then on-premises data centres, then your other AWS accounts (their VPCs, groups across a peering, PrivateLink endpoints to another account's service). A rule is too wide when it allows every protocol, a range of ports, or more addresses than one destination needs.

Read from each account's security groups as last refreshed with its flow logs (Read more data on an account refreshes them). Left out: destinations inside the account's own VPCs, AWS's own service ranges and prefix lists (S3, DynamoDB, CloudFront), transit gateway interfaces, and groups no interface uses. Internet: any public range not known as a SaaS or partner, including AWS EC2 ranges wider than a /24 (anyone's servers). SaaS and partners: ranges named in the IP lists or your names file, and single hosts on AWS. On-premises data centres: private ranges outside every VPC read; a range such as 10.0.0.0/8 that also covers other accounts' VPCs is counted here, as its riskiest reach. Other AWS accounts: another account's VPC range, a group in another account, or a PrivateLink endpoint (in this account) to another account's service. The default rule every new group gets (all traffic to 0.0.0.0/0, and to ::/0 in IPv6 VPCs) is hidden unless ticked, as it is on almost every group: it still counts in the totals. Severity: internet and too wide is high; SaaS or on-premises and too wide is medium. To narrow a rule to what is actually used, read the account with outbound flow logs (read --egress) and use its review's "Outbound wider than used".

Security groups

Rules and interfaces, region by region

Every group's rules as they stand, with anything waiting to be applied. Open a group to change a rule by hand, keep a change someone made in AWS, and Apply approved changes to make them in AWS.

A group cannot hold more than its rule limit (60 by default, set in Remediate → Narrowing settings), so replacing rules needs an order. Apply refuses any group whose final rules would be over the limit, before changing anything.

Add first, then swap (recommended): the new rules go in while the group has free rules, so a narrow rule is in place before the wide rule it replaces goes. When the group is full, one old rule is removed for each further new rule, least impact first: first rules whose traffic a new rule still lets in, then by the flow logs the rules that carried the fewest flows (unused the longest first; rules with no flow-log evidence after those), then the narrowest (fewest addresses that could lose access). Nothing is opened wider than it is now.

Bridge with a temporary rule: first adds, for each port, one temporary rule spanning every old and new source there (the smallest block covering them, not the whole internet unless an old rule already was), then swaps the rules underneath it and removes it. Nothing is cut off at any moment, but for those seconds the group lets in that whole block; if the apply stops part way, the bridge stays until the next apply removes it. Needs a free rule per port; refused otherwise. When the rule being replaced already spans the new ones, it is the bridge and is simply removed last.

Remove first, then add: every old rule goes, then the new ones are added. Uses no extra rules, but traffic the new rules allow is refused until they are in (a few seconds, longer if an add fails).
