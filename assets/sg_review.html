sg-tightener

Security Group Review

Every inbound rule in one account set against the traffic its VPC flow logs actually carried, over time. Three timelines: who was refused (needs a rule, if wanted), how many allowed addresses were never seen (over-provisioned, and what to take away), and who was let in (with sources not seen in the last 24 hours apart, so DR tests, failovers and monthly batches stand out). Each source is named: this account or a range you call internal, a data centre, AWS (and which service), a SaaS provider, or the network by AS number.

Refusals that look like something broke, and sources let in that should not have been, each with its evidence and one action, worst first, then by flows and how long it has lasted. Scans the defences turned away stay out of it: every refused source still carries its verdict in the table below.

Time window

1Refused sources

Distinct addresses turned away per period, by kind. A refused address needs a rule only if the traffic is wanted: internal and data centre sources usually are (a new service, a moved server), AWS and SaaS sometimes (health checks, webhooks, a partner's new egress), other networks rarely (scanners), so they are drawn in grey as the defences working, and in amber only in a period far above the usual level, which can mean a probe. Select a bar, or one colour in it, to list those sources; Extract rule then turns what is listed into the inbound rules that would let it in, with everything known about each source and port.

Rules that would let in the refused internal and data centre sources

Per security group and port, the refused private sources as the fewest exact ranges. Add them only if the traffic is wanted; sources a network ACL refused are left out (the ACL decides first).

2Over-provisioned addresses

For each security group with flow logs on all its interfaces, the addresses its rules let in that were never seen, summed over the groups, by kind. An address seen anywhere in the account in the whole read, let in or refused, is never counted. The rules in force at each time are worked back from today's through CloudTrail's record of rule changes (triangles: select one for the change). Rules open to every address (0.0.0.0/0) are listed below, not counted. The scale is logarithmic: each step down is a tenfold cut. The grey bars are the sources refused in each period: a tightening that went too far shows as refusals starting right after a triangle. After, at the right, is what the Tighten panel below would leave.

Tighten: how much room to leave, by kind, type and name

By source type

A type here overrides its kind: secure access services (Zscaler and the like) and CDNs usually need their published range, since their addresses move.

By name

A name here overrides its type and kind: an AWS service in one region, one partner, one of your VPCs.

Blast radius: what can one address reach?

If this host were compromised (a data centre laptop, a build server, a partner's address), every security group, port and interface its address is let in to today, and after the Tighten settings above. A rule reaches it when one of its ranges holds the address, or when it lets in a group the address's own interface is in.

Rules, and what to change

3Active sources

Distinct addresses let in per period. Dark: also let in during the last 24 hours. Light: not seen in the last 24 hours, the sources a rule change would hurt without warning (DR tests, failovers, month-end batches). Replies to the account's own outbound connections are left out. Select a bar to list its sources.

4Ports

Distinct sources per destination port over the timeline, coloured by what the port is for. Remote admin, database, Windows and directory, and container ports (marked ⚠) give control of a host or its data when reached: a refused internet source there is the rule doing its job; one let in deserves a look. Ports from 32768 up are read as one.

Port classes

5PrivateLink

Both sides of PrivateLink. Endpoint services this account provides: who may connect (any AWS account, '*', is critical when connections are also accepted without review), whether a new connection waits for acceptance, which accounts are connected, and whether the load balancer behind it applies its security groups to PrivateLink traffic. Interface endpoints in its VPCs: security groups that let in every address or a whole network (a /16 or wider), with the callers the flow logs saw and the ranges that would cover them.

6Exposure and hygiene

The configuration itself, beside the traffic. Internet exposure: an open rule is only an exposure when the internet can get there: a public address, a route to an internet gateway and a network ACL that lets it in. Each is checked, with the internet sources that connected. IPv6: ::/0 and wide global ranges, which IPv4 reviews miss. Outbound: open outbound rules, fitted to the destinations the flow logs saw (with read --egress), and connections out to Tor exits or scanners. Group hygiene: the default group in use, trust in another account's group, references to deleted groups, and one group across several tiers.
